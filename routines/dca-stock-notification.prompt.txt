--------------------------------------------------------------------------------
THE ONE RULE THAT MATTERS MOST
--------------------------------------------------------------------------------
This pipeline moves TEXT ONLY. It must never produce, encode, attach or emit a
binary payload.

  - Do NOT render a PDF.
  - Do NOT call mcp__Gmail__send_message with an `attachments` array.
  - Do NOT call mcp__Google_Drive__create_file with `base64Content`.
  - Do NOT emit any long verbatim high-entropy string as a tool-call argument.

An earlier design attached the stock report as a PDF. The stock table runs to ~176
rows across 21 columns; the resulting PDF base64 is far past the length at which a
single verbatim emission stops completing, so the run hung with the email unsent —
every time, not intermittently. Read `.claude/skills/base64-binary-payloads/SKILL.md`
and the "Why there is no PDF" section of README.md before changing anything about
delivery. The dashboard travels as the email's own HTML body, which is an ordinary
UTF-8 string parameter with no encoding step and no size cliff.

If you ever find yourself reaching for base64 here, the design has been broken.
Stop and report instead.

--------------------------------------------------------------------------------
STEP 0 — Preflight
--------------------------------------------------------------------------------
Run `ls` and locate this repository's checkout (it contains src/, routines/, tests/).
Work from its root. Confirm `python3 --version` responds. No pip install is needed —
the pipeline is pure standard library, deliberately.

Run the test suite first:  python3 tests/test_parse_stock.py
It must print "PASS". If it fails, STOP: send nothing, and report the failure. A
parser that cannot reproduce its known-good fixture must not be pointed at live data.

--------------------------------------------------------------------------------
STEP 1 — Fetch the source email
--------------------------------------------------------------------------------
You run Friday evening. The upstream system ("ArUnit") emails a stock notification
every morning at about 09:00 WIB / 02:00 UTC, so the newest one is normally this same
Friday morning's. Find it:

  mcp__Gmail__search_threads with
    query: subject:"Notifikasi Stock" newer_than:5d
    pageSize: 10

Take the NEWEST result. Its own date is the report's "as of" date.

Senders seen historically: stockdcasystem@gmail.com and ar.dutacendana@gmail.com.
Accept either; do not filter on sender, filter on the subject and take the newest.

Then read it in full:

  mcp__Gmail__get_thread with messageFormat: PLAIN_TEXT

PLAIN_TEXT matters: it renders the HTML table as a markdown pipe table, which is
exactly what the parser expects. Do not request FULL_CONTENT — the HTML body is
~480 KB and will flood your context for no benefit.

--------------------------------------------------------------------------------
STEP 2 — Guard: is the data fresh enough?
--------------------------------------------------------------------------------
The upstream system occasionally skips a day. At a weekly cadence, skipping the whole
week because Friday's send was missed is worse than reporting Thursday's position — so
accept the newest notification from the last 4 days and label it honestly.

  - Newest notification is 0-4 days old  -> proceed. The report is titled "per
    <that email's date>", never "per today". If it is not from today, say so in your
    STEP 8 summary.
  - Newest notification is older than 4 days, or there is none -> SILENT NO-OP.
    Send no email, publish nothing, report "no recent source email" and end.

Never substitute today's date for the source email's date, and never carry numbers
forward from a previous week.

--------------------------------------------------------------------------------
STEP 3 — Parse
--------------------------------------------------------------------------------
Write the `plaintextBody` you received to a working file, then:

  mkdir -p out
  python3 src/parse_stock.py out/source.md YYYY-MM-DD > out/metrics.json

where YYYY-MM-DD is the source email's date. The parser raises on a missing or empty
table rather than inventing numbers — if it raises, STOP and report.

--------------------------------------------------------------------------------
STEP 4 — Sanity gates (do not skip)
--------------------------------------------------------------------------------
Read out/metrics.json and check all four before going further:

  1. rows_in_table is at least 50. A sudden collapse to a handful of rows means the
     upstream format changed, not that the dealer sold its inventory overnight.
  2. Every entry in `reconciliation` has "match": true. These compare the source
     email's own four headline counters against a recount of its own table. A
     mismatch means either the upstream summary is wrong or the parse is wrong —
     either way a human should look before it goes out.
  3. counts.unsold is greater than 0.
  4. value.unsold_hpp is greater than 0.

If any gate fails: publish nothing, send nothing to the distribution list. Email
ONLY vwilliam@dutacendana.com with the subject prefixed "[PERIKSA]", stating exactly
which gate failed and the figures involved. Then end.

--------------------------------------------------------------------------------
STEP 5 — Render
--------------------------------------------------------------------------------
  python3 src/render_dashboard.py out/metrics.json

This writes three files, none of them binary:

  out/artifact.html   the dashboard, with HPP -- published, not emailed
  out/email-a.html    email A body, WITH HPP cost figures
  out/email-b.html    email B body, NO cost figures anywhere

Do not hand-edit any of them; change the renderer instead so the next run inherits
the fix. In particular, never produce variant B by editing variant A -- the renderer
removes whole columns and swaps the value tile for the sold count, which blanking
cells by hand would not reproduce.

Publish out/artifact.html with the Artifact tool.

--------------------------------------------------------------------------------
WHAT THE DASHBOARD SAYS, AND WHY
--------------------------------------------------------------------------------
The source email already lists every unit. Restating that list adds nothing. What it
does NOT do, and what this report exists to add:

  - Aging. Days since DO, bucketed, for unsold units only. Capital sitting in metal
    older than 90 days is the single number a dealer principal acts on, and a weekly
    rhythm is the right one for acting on it.
  - Value. HPP rolled up per bucket, per branch, per model — so "8 old units" becomes
    "Rp 1,48 M tied up".
  - Reconciliation. The source's "Total Stock" counter is FREE + MATCHING, not the
    row count. Rows that are SOLD or carry no status at all are in the same table and
    are counted by no headline figure. The dashboard states this explicitly rather
    than letting the reader assume.
  - Data quality. Duplicate DO numbers, blank chassis/engine/location, placeholder
    rows priced at Rp 0 or Rp 123. These are upstream defects worth someone's
    attention, and they are invisible in a 176-row wall of text.
